# Signature Validation System (SVS)

## Overview

SVS allows you to use ACE to test your detection signatures. This is accomplished by having ACE take actions in your environment that generates the telemetry required for the signatures to generate alerts. These alerts are then automatically consumed by the SVS subsystem. ACE is then able to report when signatures are working and when they are failing.

## Concepts

- **Detection Signal**: When a signature generates an alert. In ACE, signatures add *detection points* when they match.
- **Validation Configuration**: A sequence of steps to execute in some environment that is designed to generate the telemtry required for signature validation.
- **Validation Target**: The information required to be able to execute a test on a given target. Typically includes host information and credentials.
- **Validation Execution**: The act of executing the steps defined in a Validation Configuration.
- **Validation Detection Signal Identification (VDSI)**: The process used to determine that a given detection signal was generated from a given Validation Execution.
- **Expected Detection Signal**: An expectation that a given detection signature with match the telemetry generated by a Validation Execution.
- **Unexpected Detection Signal**: When the Validation Detection Signal Identification assigns a signal to a Validation Execution that does **not** match an Expected Detection Signal.
- **Mapping Detection Signals**: An analyst maps a Detection Signal to a Validation Configuration to say "I expect this alert to fire when we run this test."

### Terminology Clarifications

- A **detection signal** is a **detection point** in ACE.
- A **validation configuration** is a single Atomic Red Team test.
- A **validation target** is a **remote access target**.
- A **validation execution** is the tracking of the execution of a single Atomic Red Team test.
- A **validation detection signal identification** is some way to identify that a detection point belongs to the execution of a test.
- A **global validation detection signal identification** is some way to identify that a detection fired on due to a test, but did not match non-global logic.
- An **expected detection signal** is the mapping of a detection signature to a specific Atomic Red Team test.
- An **unexpected detection signal** is a **detection point** that **global validation detection signal identification** matched.

## New Supporting ACE Features

### SVS Queue

- Alerts that are assigned to the SVS configured `queue` have a separate cleanup schedule.
  - They bypass the built-in ACE cleanup schedule.
  - An alert in the SVS configured `queue` is automatically deleted when there are no references to any containing detection points in `validation_results`. 
  - The `validation_execution` table is maintained (pruned) the daily cron maintenance task.

### Credentials

A **credential** is some form of authentication data intended to be used to access remote systems.

#### Credential Type

A **credential type** defines the Python class used to handle a specific type of credential. ACE can define zero or more credential types in configuration. They have the following properties:

- `name`: a unique name for the credential type
- `python_module`: the python module to use for this credential type
- `python_class`: the python class to use for this credential type

Example configurations as follows:

```yaml
credential_types:
  - name: password
    python_module: saq.credentials.password
    python_class: PasswordCredential
  - name: ssh_key
    python_module: saq.credentials.ssh
    python_class: SSHKeyPairCredential
```

#### Credentials

A **credential** is an instance of a credential of some **credential type**. ACE can define zero or more credentials. They have the following properties:

- `type`: maps to the `name` field of a **credential type** so ACE can load it.
- `name`: a unique name for the credential
- `args`: a free form dictionary passed to the constructor for the given type

Example configurations as follows:

```yaml
credentials:
  - name: windows vm
    type: password
    args:
      username: username
      password: encrypted:password
  - name: linux vm
    type: ssh_key
    args:
      path: ~/.ssh/id_rsa
```

### Remote Access

ACE can access remote systems for the purposes of inspection and/or execution. It does so using specialized Python classes that implement remote access behavior, using defined **credentials**.

#### Remote Access Type

A **remote access type** defines the Python class that is built to access a remote system in some particular way. ACE can define zero or more remote access types. They have the following properties:

- `name`: a unique name for the type
- `python_module`: the python module to use for this credential type
- `python_class`: the python class to use for this credential type

Example configuration as follows:

```yaml
remote_access_types:
  - name: remote-powershell
    python_module: saq.remote.powershell
    python_class: PowershellRemoteAccess
  - name: ssh
    python_module: saq.remote.ssh
    python_class: SSHRemoteAccess
```

#### Remote Access Target

A **remote access target** represents some remote system that ACE has access to using some **remote access type** and supplied **credentials**. ACE can define zero or more remote access targets. They have the following properties:

- `name`: a unique name for the remote target
- `type`: maps to the `name` field of `remote_access.types` which defines *how* the target will be accessed
- `credential`: maps to the `name` field of `credentials.instances` which defines which credential to use
- `args`: a free form dictionary passed to the constructor for the given type

Example configuration as follows:

```yaml
remote_access_targets:
  - name: windows vm
    type: remote-powershell
    credential: windows vm
    args:
      ip: 10.1.1.1
  - name: linux vm
    type: ssh
    credential: linux vm
    args:
      hostname: linuxvm.local
```

## SVS Components

### Validation Configuration

The Validation Configuration defines what steps to take to generate the detection signal. SVS uses the [Atomic Red Team](https://github.com/redcanaryco/atomic-red-team) format to define the actions to take for a given Validation Execution.

### Validation Target

A Validation Target defines *where* (or, on what) a given Validation Execution occurs. Typically this is a target host, or it could be an AWS account. It depends on the test being executed.

### Validation Detection Signal Identification (VDSI)

ACE needs to be able to identify the Detection Signals generated by the Validation Execution. VDSI is logic that is able to be applied to detection points in ACE to determine the detection point was triggered by the execution of a test.

Some Validation Targets automatically apply their own VDSI. For example, a Validation Target that is a windows virtual machine might add it's hostname, local IP address and MAC address as VDSI. Analyst are free to add their own logic as well.

#### Global Validation Detection Signal Identification

An additional set of these configuration parameters can be defined at the global scope (by default that are not global). These are always in effect, regardless of what Validation Executions are currently running. These are intended to be used to catch straggler detection signals and are always assigned as Unexpected Detection Signals.

### Validation Execution

When a given Validation Configuration is executed against a Validation Target, it becomes a Validation Execution, which is just an occurance of executing the steps defined in the configuration. This is represented conceptually as an object with the following properties:

- the Validation Configuration that was used.
- one or more Validation Targets that were used (typically just one).
- the Validation Detection Signal Identification (VDSI) to use to identify detection signals.
- Validation Execution tracking data (start time, stop time, error codes, output, status)

A start and end time define the window during which any Detection Signals that match the VDSI are assigned to the Validation Execution. The end time should be calculated based on the longest possible delay by any of the Expected Detection Signals. For example, if a hunt only runs once per hour, then the end time should at least be an hour past the start time.

### Detection Signal Classification

When a VDSI matches a Detection Signal to a Validation Execution, it becomes one of the following

- An **Expected Detection Signal**: the signal was expected to be generated.
- An **Unexpected Detection Signal**: the signal was **not** expected to be generated (only applies to global VDSI).
- An **Ignored Detection Signal**: the signal was expected to be generated but should be ignored.

#### Expected Detection Signals

Analysts define which Detection Signals are expected to be generated for a given Validation Configuration through a mapping of siguture UUIDs to Validation Configuration IDs.

#### Unexpected Detection Signals

When a Detection Signal matches a VDSI, but it **does not** match the mapping of Expected Detection Signals, then the signal is considered *unexpected*. This can happen for a few reasons.

- The signal is from a new detection signature that the analysts have not mapped yet.
- The signal is from another test that was mistakenly assigned due to faulty VDSI logic or telemetry delay.
- The signal is due to setup activity that is not actually part of what is being tested (for example, running powershell remotely often fires detection signals, but might be required to execute the test.)

In all cases, the analyst can decide what to do with the signal.

- Map the Detection Signal to the Validation Configuration.
- Reassign the Detection Signal to another Validation Execution.
- Configure the Detection Signal to be ignored.
- Adjust the Validation Detection Signal Identification logic.

### Validation Results

Validation Results are computed based on the received Detection Signals. They can be computed at time during during or after the Validation Execution has started. The analysts should be able to answer the following questions.

- Which Expected Detection Signals fired?
- Which Expected Detection Signals did NOT fire?
- Which detection signals were unexpected?

# SVS Implementation Details

## Validation Configuration

SVS uses the Atomic Red Team syntax for configuration. SVS considers each element of the `atomic_tests` property of an Atomic Red Team configuration file as an individual Validation Configuration. The execution of each is tracked independantly of the others. The analysts map the Expected Detection Signals to each of these individual tests. Each Validation Configuration is identified using the `auto_generated_guid` field.

These YAML are tracked in git repositories. SVS uses ACE's built-in git integration feature (using the `git_repo_*` configuration) to checkout and update the local copy. Multiple repositories can be used.

## ACE SVS Remote Installer

The Validation Target is the target system or account that you want to use to execute the tests. **Only one test may be executed on a single Validation Target at time.** Overlapping tests on a single target must not be allowed.

A target host must be prepared ahead of time to be used as a validation target for SVS. ACE can be used to automatically configure and install the files and software needed to execute the tests. However, the ACE operators must provision the access to do so, which is outside the scope of SVS.

```bash
# ACE supports the following command to prepare a Validation Target
# TARGET is the name of the validation target in the configuration
ace svs install TARGET
```

The ACE SVS Remote Installer

- Checks to make sure the remote system can be accessed.
- Installs git.
- Installs any required git authentication files.
- Clones the git repositories.
- Installs any other required packages.
- Runs system checks for required monitoring tools.

## SVS ACE Configuration

```yaml

# git repositories containing atomic red team tests are defined

git_repo_svs_atomic_red_team:
  name: svs-atomic-red-team
  description: Atomic Red Team
  local_path: svs/atomic-red-team
  git_url: https://github.com/redcanaryco/atomic-red-team.git
  update_frequency: 3600
  branch: main
  ssh_key_path: 

git_repo_svs_site_local:
  name: svs-site-local
  description: site local atomics
  local_path: svs/local
  git_url: https://github.com/redcanaryco/atomic-red-team.git
  update_frequency: 3600
  branch: main
  ssh_key_path: 

# credentials required for remote access to validation targets

credentials:
  - name: windows vm
    type: password
    args:
      username: user
      password: pass

  - name: linux vm
    type: ssh_key
    args:
      file_path: path/to/key
      password: optional ssh password

# remote execution methods available to ACE (extendable via integrations)

remote_execution:
  - name: ssh
    python_module: saq.svs.remote.ssh
    python_class: SSHRemoteExecutor

  - type: psexec
    python_module: saq.svs.remote.psexec
    python_class: PSExecRemoteExecutor
    args:
      - username
      - password

# SVS core configuration settings

svs:
  # any alert that a detection point that matches *any* VDSI gets automatically assigned to this queue
  # the intention is to remove the alert from the main analyst work queue so they're not wasting time investigating a test alert
  queue: validation

  # list of one or more atomic red team repositories
  validation_configurations:
    - name: atomic red team
      # matches the name field of the git repo
      repo: svs-atomic-red-team
      # directory that contains the atomic tests
      # relative to the repo directory
      atomic_dir: atomics
    - name: site local tests
      repo: svs-site-local
      atomic_dir: atomics

  validation_targets:
    # matches the name field of a remote access target
    - target: window vm
      # matches the name field of a remote access type
      access_type: remote-powershell
      # matches the name field of a credential
      credential: windows vm
    - target: linux vm
      access_type: ssh
      credential: linux vm
```

## Validation Database Overview

SVS uses the ACE database to manage validation configuration and execution tracking. The following database tables are used.

- `validation_configuration`: contains one entry for every Validation Configuration.
- `validation_target`: contains one entry for every configured target
- `validation_credential`: contains one entry for every configured credential
- `vdsi`: each entry contains logic to match detection signals
- `vdsi_execution_mapping`: maps the logic to match detection signals to the test that that combination of logic should assign it to
- `validation_execution`: each entry represents the execution of a validation configuration on a validation target with the given VDSI
- `validation_expected`: contains the mapping of validation_configuration to detection signature uuid, with optional ignore flag
- `validation_results`: contains the mapping of detection signals to validation_execution

### `validation_configuration`

This table is automatically populated from the defined `validation_configuration` section.

- `id`: database unique id
- `uuid`: atomic uuid
- `name`: name of the atomic
- `description`: english description of the atomic
- `

### `vdsi`

- `id`: database unique id
- `type`: identification type (hostname, ip, mac, username, aws_account, etc...)
- `match_type`: type of string match (string, glob, regex, cidr)
- `match_value`: the value to match (format depends on match_type)
- `is_global`: boolean if always in effect

### `validation_execution`

- `id`: database unique id
- `insert_date`: when the record was created, used when pruning
- `configuration_id`: FK to `validation_configuration.id`
- `target`: what system/credentials to use to execute the test
- `start_time`: when the test started
- `end_time`: when the test is considered finished
- `stdout`: raw stdout captured from running the test
- `stderr`: raw stderr captured from running the test
- `exitcode`: final exit code of running the test
- `status`: current status of the test (NEW, ERROR, RUNNING, COMPLETED)

### `vdsi_execution_mapping`

- `execution_id`: FK to `validation_execution.id`
- `vdsi_id`: FK to `vdsi.id`

### `validation_expected`

- `configuration_id`: FK to `validation_configuration.id`
- `signature_uuid`: the uuid of the signature
- `ignore`: boolean

### `validation_results`

- `execution_id`: FK to `validation_execution.id`
- `signature_uuid`: the uuid of the signature
- `detection_point_id`: FK to `detection_points.id`

## Operations

This section details how SVS works.

### Database Sync

ACE automatically updates the following internal database tables based on configuration data on a regular cron job.

- `validation_configuration` is automatically sync'd with the configured git repositories

### Test Execution 

This section explains the steps an analyst and ACE take to fully execute a test from start to finish.

1. Analyst selects which Validation Configuration to execute.
1. Analyst selects which Validation Target to execute the tests on.
1. Analyst optionally adds additional Validation Destection Signal Identification data.
1. Analyst reviews and starts the test.
1. ACE uses the information in the `validation_remote_execution` section to remotely access the validation target.
1. ACE prepares the target system for the execution of the test.
1. ACE records when the testing starts.
1. ACE executes the test remotely.
1. ACE records the stdout, stderr and exit codes of the remote execution.
1. ACE records when the testing officially stopped.

### Test Alert Automatic Dispositioning

This section explains how ACE handles alerts created by the execution of tests.

1. SVS automatically analyzes an Alert when the analysis of the Alert starts and when it finishes.
1. SVS compares the VDSI configured for the Validation Execution against the alert.
1. If any non-global VDSI match a **running** Validation Execution, then ACE does the following:
  - populates `validation_results` table with the entry
  - reassigns the alert to the configured queue
  - dispositions the alert as 
      - **IGNORED** if the Expected Detection Signal is set to ignore.
      - **REVIEWED** otherwise.
1. If any **global** VDSI matches, then ACE simply reassigns the alert to the configured queue. It is up to the analyst to review the alert and assign it to the correct test, or IGNORE it.
